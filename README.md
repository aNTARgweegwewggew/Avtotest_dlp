# DLP-автотесты

Проект отправляет тестовые письма и загружает тестовые файлы. После отправки
тесты проверяют, появилась ли передача в базе DLP. Файлы в `tests/data`
синтетические и не содержат реальных данных.

## Карта проекта

| Путь | Назначение |
|---|---|
| `src/smtp/` | Отправка тестовых писем через SMTP; чтение через IMAP и POP3 |
| `src/database/` | Поиск текста письма и DLP-инцидента в PostgreSQL |
| `src/mail/` | Интеграции с Яндекс.Диском, Яндекс.Почтой и Google Drive |
| `src/telegram/` | Отправка Telegram-сообщения от личного аккаунта и отдельный вход |
| `tests/smtp/` | Реальные SMTP/IMAP/POP3 и проверки DLP в базе |
| `tests/browsers/` | Реальные загрузки и скачивания в облачных сервисах |
| `tests/mail/` | Локальные проверки формирования запросов и писем без внешней отправки |
| `tests/telegram/` | Интеграционная отправка сообщения тестовому Telegram-пользователю |
| `tests/data/` | Синтетические тексты и файлы, используемые тестами |
| `conftest.py` | Загрузка `.env`, соединение с БД, OAuth-токены и ожидание результатов |

Почтовый DLP-сценарий проходит так: создаётся письмо с уникальным ID,
отправляется на стенд, тест ограниченное время ищет этот ID в PostgreSQL и
сравнивает найденный текст и, если есть, имена вложений. Облачные тесты
сверяют загруженный и скачанный файл; DLP-инцидент дополнительно проверяется
в консоли ZGate.

## Первый запуск

На новом Linux-стенде один раз скачайте стартовый скрипт и запустите его:

```bash
curl -fsSLO https://raw.githubusercontent.com/aNTARgweegwewggew/Avtotest_dlp/main/start_tests.sh
bash start_tests.sh
```

Скрипт клонирует проект в `~/Avtotest_dlp`, создаёт `.venv`, устанавливает
зависимости и создаёт `.env` из `.env.example`, если `.env` ещё нет. Затем он
показывает меню с каталогами тестов.
Для скачивания нужны `git` и доступ стенда к GitHub. Для приватного репозитория
настройте Git-аутентификацию на стенде; не добавляйте пароль или токен в скрипт.

Если в `~/Avtotest_dlp` уже есть этот проект, скрипт использует его и не
перезаписывает файлы. Если папка занята чем-то другим, скрипт остановится;
укажи другое место командой:

```bash
PROJECT_DIR="$HOME/dlp-tests" bash start_tests.sh
```

После первого запуска открой `.env`, заполни настройки выбранных тестов и
снова запусти скрипт командой `bash start_tests.sh` из папки проекта.
Скрипт предложит выбрать папку. После запуска тестов меню появится снова;
выбери `0`, чтобы выйти. Код завершения скрипта покажет результат последнего
запуска тестов. Чтобы запустить одну папку напрямую, например:

```bash
.venv/bin/python -m pytest -v tests/telegram
```

Если проект клонировали вручную и файла `.env` ещё нет, создай его из шаблона
и редактируй настройки только в `.env`:

```bash
cp .env.example .env
nano .env
```

Тестовый код читает значения из `.env`; не вставляй логины, получателей или
ключи прямо в `.py` файлы. `.env.example` — только шаблон без рабочих секретов.

`PASSED` означает, что проверки пройдены. `SKIPPED` означает, что для теста
не задан обязательный сервис или токен. `FAILED` означает, что тест не прошёл;
причина будет указана в выводе.

## Запуск тестов

Из корня проекта:

```bash
# Локальные проверки; не отправляют письма, не обращаются к облакам или БД
.venv/bin/python -m pytest -v -m "not integration"

# Один локальный тест формирования запроса
.venv/bin/python -m pytest -v tests/mail/test_google_drive_upload.py

# Интеграционные проверки; требуют соответствующих сервисов и секретов
.venv/bin/python -m pytest -v -m integration

# Все тесты (включая реальные отправки и загрузки)
.venv/bin/python -m pytest -v
```

Каталоги `tests/smtp/` и `tests/browsers/` и Telegram-отправка отмечены как
интеграционные. Некоторые тесты пропускаются, если не настроен OAuth-токен;
почтовые проверки при отсутствии обязательных параметров завершаются понятной
ошибкой конфигурации. Интеграционные тесты могут отправлять реальные письма и
файлы. Не запускайте одновременно несколько тестов с одной почтовой записью
или Telegram-сессией.

| Группа | Что требуется |
|---|---|
| `tests/smtp/` | SMTP/IMAP/POP3-сервер и `MAIL_*`; DLP-проверкам также нужны `DB_*` |
| DLP-письма Яндекса | OAuth-файл `YANDEX_MAIL_TOKEN_FILE`, `YANDEX_MAIL_*` и `DB_*` |
| Яндекс.Диск | OAuth-файл `YANDEX_TOKEN_FILE`, API доступ и `YANDEX_DISK_TEST_FOLDER` |
| Google Drive | OAuth-файл `GOOGLE_DRIVE_TOKEN_FILE`, `GOOGLE_DRIVE_TEST_FOLDER_ID` и API доступ |
| Telegram | `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_TEST_USERNAME` и заранее созданная сессия |
| Google Search | Только если явно задано `RUN_GOOGLE_SEARCH_TESTS=1` |

Файлы OAuth создаются отдельно от `.env` и не входят в Git:

- Для Яндекс.Диска `YANDEX_TOKEN_FILE` должен указывать на JSON с
  `access_token` и `refresh_token`. При ответе API `401` тест использует
  `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` для обновления токена и сохранит
  обновлённый файл.
- Для Яндекс.Почты `YANDEX_MAIL_TOKEN_FILE` должен указывать на JSON с
  `access_token`.
- Для Google Drive `GOOGLE_DRIVE_TOKEN_FILE` должен указывать на JSON OAuth
  credentials с правом доступа к Drive. При наличии refresh token тест
  обновляет credentials и сохраняет их. Скрипт
  `scripts/authorize_google_drive.py` предназначен для повторной OAuth-
  авторизации при уже существующем OAuth-файле, а не создаёт начальные
  credentials с нуля.

Не копируйте OAuth-файлы в репозиторий. На стенде задайте пути к ним в `.env`
и ограничьте доступ к каталогу с файлами секретов.

Письма, созданные для тестов SMTP/Яндекс.Почты, и записи DLP из PostgreSQL
тесты автоматически не удаляют. Не запускайте их на рабочем ящике или
production-базе. Тесты Яндекс.Диска удаляют собственную папку конкретного
запуска; Google Drive удаляет только загруженный тестовый файл.

### Добавление теста

1. Выбери соседний пример: `tests/mail/` для локальной проверки запроса или
   `tests/smtp/` / `tests/browsers/` для реального стенда.
2. В тесте явно задай синтетические данные и выполни одно проверяемое действие.
3. Для теста, который обращается к внешнему сервису, добавь
   `@pytest.mark.integration` и проверь удаление только собственных тестовых
   данных.
4. Запусти сначала один файл, затем нужную группу. Для интеграционного теста
   проверь конфигурацию и тестовые учётные записи до запуска.

## Тесты почты

### Общий SMTP-стенд

Параметры `MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM` и
`MAIL_TO` нужны для общего стенда. Тесты отправляют сообщения через SMTP и
читают их через IMAP или POP3. DLP-тесты дополнительно ищут текст письма и
инцидент в настроенной базе PostgreSQL.

### Яндекс.Почта

Для Яндекс.Почты используются отдельный OAuth-токен и отдельные настройки:
`YANDEX_MAIL_TOKEN_FILE`, `YANDEX_MAIL_USERNAME` и `YANDEX_MAIL_TO`.
`YANDEX_MAIL_FROM` можно не задавать — тогда отправителем будет
`YANDEX_MAIL_USERNAME`. По умолчанию используются `smtp.yandex.com` и порт
`465`; также поддерживается порт `587` с STARTTLS.

Создайте файл, например `secrets/yandex_mail_token.json`, с таким форматом:

```json
{
  "access_token": "вставьте_токен_сюда"
}
```

Этот токен должен быть выдан для почтового аккаунта и поддерживать OAuth-вход
в SMTP. Токен Яндекс.Диска не заменяет почтовый токен. Тесты авторизуются на
SMTP через XOAUTH2; пароль почты им не нужен.

Яндекс Mail REST API позволяет читать и изменять письма, но не отправлять их.
Поэтому отправка выполняется через SMTP, а токен используется для
авторизации. См. [документацию Яндекс.Почты](https://yandex.com/dev/yandex-360/mail/ru/)
и [настройку почтового клиента](https://yandex.com/support/yandex-360/customers/mail/en/mail-clients/others.html).

Запускаются три отдельных DLP-сценария:

1. Письмо с текстом и уникальным ID.
2. Такое же письмо с одним вложением.
3. Такое же письмо с двумя вложениями.

Каждый сценарий отправляет письмо, ждёт DLP-инцидент и сверяет текст и имена
вложений с данными в базе. Для этих проверок должны быть заданы параметры
PostgreSQL `DB_HOST`, `DB_NAME`, `DB_USER` и `DB_PASSWORD`.
Для этих тестов используйте отдельную тестовую БД и пользователя с правом
чтения нужных представлений `zinc_v_blob` и `zinc_v_source`. Проверки только
читают записи и не удаляют данные из базы. Схему и правила формирования
инцидентов тесты не меняют.

## Облачные диски

Яндекс.Диск и Google Drive используют собственные OAuth-токены и свои тестовые
папки. Облачные тесты загружают файл, скачивают его, сравнивают содержимое и
удаляют тестовые данные. Успешная загрузка сама по себе ещё не доказывает,
что DLP создала инцидент: проверьте событие в консоли ZGate.

## Отправка сообщения из Telegram

Эти шаги настраивают отправку сообщения **от личного аккаунта**, не от бота.
Выполняйте их в терминале нового Linux-стенда.

1. Выполните первый запуск проекта по инструкции выше. Скрипт сам установит
   зависимости и создаст `.env`.
2. Открой `.env` в папке проекта и заполни `TELEGRAM_API_ID`,
   `TELEGRAM_API_HASH` и `TELEGRAM_TEST_USERNAME` реальными значениями.
   Эти настройки задаются только в `.env`, не в Python-коде.

   `API ID` и `API hash` создаются на
   [my.telegram.org](https://my.telegram.org). Если сайт недоступен без VPN,
   получите значения в браузере через VPN и затем внесите их в `.env` на
   стенде. Не присылайте эти значения в чат и не добавляйте `.env` в Git.

3. Один раз авторизуйте аккаунт в интерактивном терминале:

   ```bash
   .venv/bin/python -m src.telegram.authorize
   ```

   Введите номер телефона, код Telegram и, если запросит, пароль двухэтапной
   проверки. Авторизация создаёт `secrets/telegram_user.session`.
4. Запустите Telegram-тест:

   ```bash
   .venv/bin/python -m pytest -v tests/telegram
   ```

   Тест отправляет реальное сообщение на `TELEGRAM_TEST_USERNAME` из `.env`.
   Если параметр не задан, тест будет пропущен. Обычный запуск pytest не
   запрашивает номер, код или пароль; если сессия отсутствует или истекла,
   тест завершается с инструкцией повторить авторизацию вручную. Успех
   означает, что Telegram вернул ID отправленного сообщения; этот тест сам по
   себе не проверяет создание DLP-инцидента.

После входа Telethon создаст `secrets/telegram_user.session`. Это локальный
файл авторизации, а не API-ключ: он позволяет пользоваться вашим аккаунтом.
Не отправляйте его другим, не переносите на общий сервер без необходимости и
не добавляйте в Git. Он хранится в закрытом каталоге `secrets/`; каталог и
файл сессии игнорируются Git. Удаление session потребует пройти вход ещё раз.

Стенд должен сам подключаться к серверам Telegram. VPN, включённый только на
вашем компьютере, не меняет сетевой маршрут Linux-сервера. Если соединение с
Telegram со стенда недоступно, команда завершится сетевой ошибкой.

## Переменные окружения

Все доступные настройки перечислены в `.env.example`. Указывайте только
настройки тех сценариев, которые собираетесь запускать. Если тест требует
базу, учётную запись или токен, но настройка отсутствует, он будет пропущен
или завершится понятной ошибкой при некорректном значении.

Не коммитьте `.env`, OAuth-токены, пароли и логи с данными тестового стенда.
