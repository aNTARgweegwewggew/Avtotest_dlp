# Автотесты DLP

Этот проект — начало набора автотестов для проверки DLP. Тесты сами отправляют
письма и загружают небольшие тестовые файлы в облачные диски. Так можно
проверить, что сервис принял данные, а затем найти событие в консоли ZGate.

Тесты не меняют исходные файлы стенда: примеры для загрузки хранятся в
`tests/data`. Облачные проверки создают отдельные папки и файлы, а затем
удаляют их. Почтовые сообщения тесты не удаляют.

Пока это не готовый CI/CD-конвейер. Сначала тесты нужно запускать вручную и
проверять результат; позже их можно подключить к TeamCity.

## Где запускать

Тесты можно запускать на Linux-сервере или локально. Для проверки работы с
ZGate удобнее запускать их на машине, через которую проходит трафик.

На Linux подготовьте окружение один раз:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Создайте в корне проекта файл `.env` и заполните нужные для выбранных тестов
настройки. Не отправляйте этот файл в Git: в нём могут быть пароли и пути к
OAuth-токенам.

Запустить весь набор тестов:

```bash
python -m pytest -v
```

Запустить только проверки почты:

```bash
python -m pytest tests/smtp -v
```

Запустить проверки облачных дисков:

```bash
python -m pytest -v \
  tests/browsers/test_upload_file_in_google_drive.py \
  tests/browsers/test_upload_file_in_yandex_disc.py
```

## Тестовый runner без CI-сервера

Пока GitLab CI, Jenkins и TeamCity не подключены, на Linux-стенде можно
запускать тесты через общий скрипт:

```bash
./scripts/run_tests.sh quick
./scripts/run_tests.sh google
./scripts/run_tests.sh cloud
./scripts/run_tests.sh mail
./scripts/run_tests.sh all
```

`quick` запускает быстрые локальные тесты без обращения к сети. `google`
проверяет только Google Drive. `cloud` проверяет реальные передачи в Google
Drive и Яндекс.Диск;
`mail` запускает сценарии почтового стенда; `all` запускает весь набор.
Облачные и почтовые тесты требуют соответствующих настроек в `.env`.

Для каждого запуска скрипт сохраняет полный вывод pytest, код завершения и
краткий итог в отдельную папку `artifacts/test-runs`. В логах могут быть
диагностические данные, поэтому папки результатов доступны только владельцу
на Linux и исключены из Git. Не публикуйте их без проверки.

Запускайте скрипт из корня проекта. Для пилотного режима его можно вызывать
вручную после обновления кода; он же может стать командой запуска runner при
подключении CI. Пока CI-сервера нет, тесты автоматически после каждого
изменения не запускаются.

Если нужная настройка не указана, соответствующий тест будет пропущен. Ошибка
подключения или неожиданный ответ сервиса считаются ошибкой теста, а не
успешным результатом.

## Что проверяется

- Почтовые тесты отправляют письма и проверяют их получение по уникальному
  маркеру. Используются SMTP, POP3 и IMAP.
- Тест Яндекс.Диска создаёт отдельную папку для запуска, загружает файл,
  скачивает его, сравнивает содержимое и удаляет папку.
- Тест Google Drive загружает файл, скачивает его по ID, сравнивает содержимое
  и удаляет этот файл.
- Тест поиска Google запускается только при `RUN_GOOGLE_SEARCH_TESTS=1`.
- Облачные тесты не проверяют запись в DLP-базе. После успешной загрузки
  проверьте в консоли ZGate, появилось ли нужное событие. Почтовый тест
  проверки DLP-событий использует настройки базы данных, если они заданы.

В тестовых файлах используется синтетический маркер `secret password` и
уникальный ID запуска. Это помогает найти тестовую передачу в журналах и
консоли инцидентов.

## Настройки

Скопируйте [.env.example](./.env.example) в `.env` и заполните только настройки
нужных тестов. Например, на Linux:

```bash
cp .env.example .env
```

Пример содержит вымышленные значения — замените их своими. Секреты и адреса
стенда остаются в локальном `.env` и не добавляются в Git.

### Почта

Нужны адрес и учётные данные тестового почтового сервера:

```dotenv
MAIL_HOST=адрес_почтового_сервера
MAIL_USERNAME=тестовый_пользователь
MAIL_PASSWORD=пароль_тестового_пользователя
MAIL_FROM=адрес_отправителя
MAIL_TO=адрес_тестового_получателя
```

Адреса отправителя и получателя обязательны: в коде больше нет адресов
конкретного пользователя. Старые имена `HOST_MAIL`, `USERNAME` и
`PASSWORD_MAIL` пока поддерживаются для существующих конфигураций; для новых
используйте имена из примера.

Для поиска DLP-событий в PostgreSQL задайте `DB_HOST`, `DB_NAME`, `DB_USER` и
`DB_PASSWORD`. Старые имена `host`, `dbname`, `user` и `password` также
поддерживаются. Если все параметры базы не заданы, только тест DLP-инцидента
будет пропущен; частично заполненная конфигурация считается ошибкой.

Порты почтовых протоколов можно задать списками через запятую:
`SMTP_TEST_PORTS`, `POP3_TEST_PORTS` и `IMAP_TEST_PORTS`. Таймаут ожидания
письма настраивается через `MAIL_DELIVERY_TIMEOUT_SECONDS`, а ожидание
DLP-события — через `DLP_INCIDENT_TIMEOUT_SECONDS`.

### Яндекс.Диск

Укажите `YANDEX_TOKEN_FILE` — путь к файлу OAuth-токена. Если токен нужно
обновлять автоматически, также задайте `YANDEX_CLIENT_ID` и
`YANDEX_CLIENT_SECRET`.

Тест создаёт папку внутри `YANDEX_DISK_TEST_FOLDER`. Если параметр не задан,
используется `/DLP_AUTOTEST`. Для тестов лучше завести отдельный аккаунт и
отдельную папку.

Яндекс.Диск сначала выдаёт временную ссылку, затем файл передаётся на неё
отдельным `PUT` с исходными байтами. Это соответствует
[официальной документации API Яндекс.Диска](https://yandex.com/dev/disk-api/doc/en/reference/upload);
файл не упаковывается в форму `multipart/form-data`.

### Google Drive

Укажите два параметра:

- `GOOGLE_DRIVE_TOKEN_FILE` — путь к OAuth-файлу с доступом к Google Drive;
- `GOOGLE_DRIVE_TEST_FOLDER_ID` — ID отдельной папки на Google Drive, куда
  тесту разрешено загружать, читать и удалять файлы.

Google-тест пропускается, если тестовая папка не настроена. OAuth-токен должен
давать доступ `https://www.googleapis.com/auth/drive`.

Загрузка выполняется одним запросом, который содержит и описание файла, и его
содержимое. Это сделано, чтобы шлюзу было проще увидеть содержимое передачи.

Для повторной OAuth-авторизации запустите `python scripts/authorize_google_drive.py`
на машине, где открыт браузер и доступен Google. Скрипт берёт настройки OAuth
из файла `GOOGLE_DRIVE_TOKEN_FILE`, поэтому в нём уже должны быть настройки
OAuth-клиента. Если запускать скрипт на удалённом сервере, понадобится
SSH-туннель для локального порта `8765`. Токен сохраняется только после
успешного согласия Google. Не пересылайте токен в сообщениях и не добавляйте
его в Git.

Если сервер не доверяет сертификату при обращении к Google или Яндексу,
установите на сервер доверенный сертификат организации и настройте
`REQUESTS_CA_BUNDLE` или `CURL_CA_BUNDLE`. Отключать проверку HTTPS не
рекомендуется.

## Как читать результат

`PASSED` означает, что проверки теста прошли. `SKIPPED` означает, что для теста
не настроен нужный сервис или параметр. `FAILED` или `ERROR` означают, что
проверка не прошла: в выводе pytest будет причина.

Успешный HTTP-ответ облачного сервиса сам по себе ещё не подтверждает создание
DLP-инцидента. После облачного теста найдите файл или его уникальный маркер в
консоли ZGate. Так отдельно проверяются передача файла и реакция DLP.
